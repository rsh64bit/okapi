Crate walkthrough — where _dispatch_core_interrupt actually comes from
Crates: riscv-rt + riscv-macros
Key fact: it's generated, not hand-written
riscv-rt/src/interrupts.rs→riscv/#[pac_enum]→riscv-macros/src/riscv.rs·macro expansion chain
What you write / what ships interrupts.rs
The entire module is just an enum
Standard RISC-V cause codes only — nothing Andes-specific:
#[riscv::pac_enum(unsafe CoreInterruptNumber)]
enum Interrupt {
    SupervisorSoft = 1,
    MachineSoft = 3,
    SupervisorTimer = 5,
    MachineTimer = 7,
    SupervisorExternal = 9,
    MachineExternal = 11,
}
The doc comment says it outright
"If your target has custom core interrupt sources... you may need to opt out this module. To do so, activate the custom-interrupts feature." — this is exactly the Andes AndeStar V5 situation.
What #[pac_enum] expands it into generated
riscv-macros/src/riscv.rs:262-285
The macro emits a lookup table + the dispatch function itself:
pub static __CORE_INTERRUPTS:
  [Option<unsafe extern "C" fn()>; N] = [ ... ];

#[no_mangle]
unsafe extern "C" fn _dispatch_core_interrupt(code: usize) {
    extern "C" { fn DefaultHandler(); }
    match __CORE_INTERRUPTS.get(code) {
        Some(Some(handler)) => handler(),
        _ => DefaultHandler(),
    }
}
Net effect
Array lookup by raw mcause code → call registered handler → else DefaultHandler(). No AndeStar semantics anywhere in this chain.

Crate walkthrough — the override point, and the v-trap alternative
Feature: custom-interrupts
Alt: v-trap (standard vectored, not AndeStar)
riscv-rt feature flags·lib.rs:585-620·what Andes support actually requires
custom-interrupts the real hook
Cargo.toml
[dependencies.riscv-rt]
version = "0.18"
features = ["custom-interrupts"]
Effect (lib.rs:718-719)
Excludes the entire interrupts module — enum, __CORE_INTERRUPTS table, generated _dispatch_core_interrupt all disappear from the build.
#[cfg(not(feature = "custom-interrupts"))]
pub mod interrupts;   // gone when the feature is on
What you must then supply
start_trap_rust still calls _dispatch_core_interrupt(code) as extern "C" — link fails without your own definition:
#[no_mangle]
unsafe extern "C" fn _dispatch_core_interrupt(code: usize) {
    // your AndeStar-aware routing here —
    // interpret `code` under AndeStar semantics
}
v-trap standard vectored, not mtvt
What it changes
_setup_interrupts sets mtvec to Vectored mode pointing at a generated _vector_table — a list of j _start_INTERRUPT_trap jumps, one per cause code.
Why it isn't a drop-in AndeStar fix
RISC-V standard vectored mode computes the target as mtvec_base + 4×cause — hardware-computed offset into one table. AndeStar's mtvt is a separate base-address CSR with its own table layout. Same idea, different mechanism.
Bottom line
Worth testing in isolation, but likely still needs custom code for true AndeStar vectoring — custom-interrupts is the dependable path today.

Okapi RTOS

The question — riscv-rt, a PLIC crate, or write our own?
Need: Andes PLIC interrupt controller
Decision: own driver inside Okapi
decision record·interrupt controller sourcing·2026-10-01
Verdict
Keep riscv-rt for trap entry. Write the Andes PLIC as our own module inside Okapi. — do not fork riscv-rt, do not adopt a generic PLIC crate.
1 · riscv-rt owns trap entry, not routing
It gives reset, .data/.bss init, mtvec setup and mcause dispatch — the CLINT-level world. It stops at “an external interrupt arrived” (MachineExternal, cause 11) by design.
Deciding which of 50+ device sources fired, at what priority, under what threshold, is the PLIC's job — intentionally out of scope for the runtime crate.
2 · The Andes PLIC is not the standard PLIC
Differences are real, not cosmetic: a PLIC + PLIC_SW pair, vendor base addresses (not SiFive's 0x0C00_0000), and a preemptive priority / nested-interrupt scheme driven by vendor CSRs the standard spec has no notion of.
A generic crate models the standard map and gives us nothing for the Andes-specific parts.
3 · For an OS, the PLIC is a kernel subsystem
Okapi is at main.rs with an empty loop {} today. The PLIC becomes load-bearing for the scheduler (timer-tick preemption), the device model, and the IRQ-masking / critical-section primitives.
That is architecture to own and shape, not inherit from a crate designed for single-app bare-metal firmware.

Okapi RTOS

Standard PLIC vs. Andes PLIC — the differences that decide it
Spec: RISC-V PLIC
Reality: AndeStar V5 / N25F
why a generic crate does not fit·four concrete divergences
Standard PLIC what crates model
Single controller
One PLIC instance. Software interrupts / IPIs are the CLINT's problem, via msip.
Canonical base address
SiFive-derived maps put it at 0x0C00_0000; crates frequently hardcode or default to it.
Flat priority, no nesting
Per-source priority + per-context threshold gate whether an IRQ is presented. The spec says nothing about preempting a handler that is already running — nesting is left entirely to software.
Standard CSRs only
mstatus, mie, mip, mcause, mtvec. Nothing vendor-specific.
Andes PLIC what N25F actually has
PLIC + PLIC_SW pair
A second controller, PLIC_SW, dedicated to software/IPI interrupts — its own base address and register block. A standard-PLIC abstraction has no slot for it.
Vendor base addresses
Comes from the core configuration, not the spec. Must be read off the AndeSight BSP / nds_ headers for our specific build.
Preemptive priority / nested IRQs
Andes adds a hardware-assisted nesting scheme via vendor CSRs. The discipline — save mepc/mstatus/mcause, re-enable, claim, complete, restore — is the vendor's, not the spec's.
Vendor CSRs in the hot path
mxstatus for the AndeStar extensions, mmisc_ctl for interrupt behaviour (e.g. vectored-plus). Touching these is mandatory, and no generic crate exposes them.

The one boundary that matters
drivers/plic.rs knows register offsets and nothing else. irq.rs is what the rest of Okapi calls, and it never mentions the PLIC by name.
Consequence: moving to a different Andes part — or adding PLIC_SW for IPIs on a multicore variant — changes one file.
Responsibility split per file
drivers/plic.rs hardware
Volatile MMIO against the Andes map: priority[], pending[], enable[], threshold, claim/complete. No kernel types, no handler table.
irq.rs policy
Handler registration table, mask/unmask, dispatch by IRQ id. The scheduler and drivers talk to this.
arch/trap.rs glue
Bridges riscv-rt's core-interrupt macro to irq::dispatch, and owns nesting (save/restore of mepc, mstatus, mcause).
arch/andes.rs vendor
Raw CSR access for AndeStar-only bits. Isolated so a non-Andes port can swap this file alone.

The dispatch path — MachineExternal to device handler
Key detail: claim in a while loop
Not: a single claim per trap
arch/trap.rs→drivers/plic.rs→irq.rs·the hot path
1
Device asserts → PLIC gates it → core takes cause 11
The PLIC presents the IRQ only if its priority exceeds the context threshold. riscv-rt's start_trap_rust decodes mcause and routes to the MachineExternal handler.
↓
2
Okapi's handler claims in a loop arch/trap.rs
Several sources can be pending behind one core line, and the PLIC deasserts only once all are completed. A single claim() per trap would silently drop the rest — so loop until the PLIC returns id 0.
#[riscv_rt::core_interrupt(CoreInterrupt::MachineExternal)]
fn machine_external() {
    // loop, not a single claim: PLIC can have several pending
    while let Some(irq) = plic::claim() {
        irq::dispatch(irq);
        plic::complete(irq);
    }
}
note: requires the CoreInterrupt enum from riscv; see slide 6 for the custom-interrupts variant
↓
3
Claim / complete handshake drivers/plic.rs
Reading the claim register atomically returns the highest-priority pending id and clears its pending bit. Writing the same id back to the complete register tells the gateway it may forward the next one. Claim id 0 means nothing pending — that is the loop's exit condition.
pub fn claim() -> Option<u32> {
    let id = unsafe { read_volatile(CLAIM) };
    (id != 0).then_some(id)      // 0 == no interrupt pending
}
pub fn complete(irq: u32) {
    unsafe { write_volatile(CLAIM, irq) }   // same register
}
↓
4
Dispatch to the registered handler irq.rs
Index the handler table by IRQ id and call it. This is the layer the scheduler hooks for timer-tick preemption, and the only layer device drivers ever see.

Whether this core config includes the software-interrupt controller at all. Determines if irq.rs needs an IPI path now or later.

Sources, in order of authority
1 · Andes core configuration report for this SoC build
